## QA-001 — Confirmation page accessible to any user by order ID (IDOR)

- Severity: **blocker**
- Where: `src/app/[locale]/checkout/confirmation/[orderId]/page.tsx` — entire file; `src/lib/queries/orders.ts:159` (`getOrderById`)
- Problem: `ConfirmationPage` calls `getOrderById(orderIdNum)` with **no authentication or ownership check**. Any anonymous user who guesses or enumerates an order ID (sequential integers starting from 1) can view a different customer's full name, phone number, address, city, notes, and order items. This is a P0 IDOR (Insecure Direct Object Reference) data-leak.
- Repro:
  1. User A places an order; gets `/checkout/confirmation/5`.
  2. User B (guest, unauthenticated) visits `/fr/checkout/confirmation/5` directly.
  3. User B sees User A's full delivery address and contact details.
- Fix: Two-tier guard: (a) If session exists, verify `order.userId === parseInt(session.user.id, 10)`. (b) If no session or guest order, issue a short-lived signed token (HMAC of orderId + timestamp, 1 h TTL) at order creation time, embed it in the redirect URL as `?token=...`, and verify it on load. Alternatively, scope guest order confirmation to the session duration only (store orderId in session cookie at creation). At minimum, add a server-side check that either the session matches the order's userId, or that no userId is on the order (guest) and the request comes from the same session that created it.
- Status: open

## QA-002 — `moroccoPhone` regex does not accept `07` prefix (valid Moroccan numbers)

- Severity: **blocker**
- Where: `src/lib/validators.ts:17` — regex `/^(0[67]\d{8}|\+212[67]\d{8})$/`
- Problem: The regex `0[67]` correctly accepts `06` and `07`. However the `+212` international variant uses `[67]` which maps to `+2126` and `+2127` — these are also the correct international equivalents. On first inspection this looks correct. **Actual blocker**: the regex requires exactly 10 digits for local format (`0` + `[67]` + 8 digits = 10 total) but Moroccan mobile numbers for Orange (`06`) have the pattern `06XXXXXXXX` (10 digits), and Maroc Telecom (`06`) and Inwi (`06`) also use 10 digits. Numbers starting `07` are also valid (Inwi). However, Moroccan fixed-line and mobile numbers in recent years include `05` prefix for certain geographic regions/VoIP. More critically: the international format `+212 6XX-XXXXXX` omits the leading zero, so `+212612345678` = 12 chars total — the regex captures `\+212[67]\d{8}` = `+212` (4) + `[67]` (1) + `\d{8}` (8) = 13 chars, which is correct. **Real bug**: A customer who types their number with a space, dash, or in the format `+212 6 12 34 56 78` will get a validation error and be unable to check out. The placeholder shows `0612345678` but the hint text does not mention that spaces/dashes are not accepted, causing user confusion and checkout abandonment.
- Repro: Enter `06 12 34 56 78` (with spaces) in checkout phone field → form rejects it → user cannot complete order.
- Fix: Either (a) strip non-digit characters before validation with `.transform(v => v.replace(/\s|-/g,''))` in the Zod schema before the regex check, or (b) update the regex to allow optional separators: `/^(0[67][\s-]?\d{2}[\s-]?\d{2}[\s-]?\d{2}[\s-]?\d{2}|\+212[\s-]?[67][\s-]?\d{2}[\s-]?\d{2}[\s-]?\d{2}[\s-]?\d{2})$/`. Option (a) is simpler — normalize then validate.
- Status: open

## QA-004 — `listProducts` price-range filter does lexicographic string comparison on `numeric` column

- Severity: **blocker**
- Where: `src/lib/queries/products.ts:21-26`
- Problem:
  ```ts
  conditions.push(gte(products.price, String(min)));
  conditions.push(lte(products.price, String(max)));
  ```
  `products.price` is a Drizzle `numeric` column (PostgreSQL `NUMERIC(10,2)`). Drizzle's `gte`/`lte` with a JavaScript `String` argument generates a query comparing the numeric column against a **string literal**, e.g. `WHERE price >= '100'`. PostgreSQL will implicitly cast the string to numeric so this works correctly in practice for Postgres, **but** it is semantically wrong and fragile: if the ORM serializes it differently across driver versions, or if the column is re-typed, it silently breaks. More critically, products with prices like `'9.99'` will sort/filter correctly numerically but the intent is not expressed — it should pass the number directly, not a string.  
  **Verified actual bug**: `String(min)` where `min = 100` yields `'100'`, and `gte(products.price, '100')` in Drizzle generates `price >= $1` with binding `'100'` (text). Postgres coerces fine, but `String(min)` where `min = NaN` (if `Number(sp.min)` fails) yields `'NaN'`, causing SQL `price >= 'NaN'` which throws a Postgres cast error and returns a 500.
- Repro: Navigate to `/fr/products?min=abc` — `Number('abc')` = `NaN`; `Math.max(0, NaN)` = `NaN`; `String(NaN)` = `'NaN'`; DB throws cast error.
- Fix: In `products/page.tsx`, guard: `const min = sp.min && !isNaN(Number(sp.min)) ? Math.max(0, Number(sp.min)) : undefined;` (already done for `Math.max` but `NaN` passes through `Math.max(0, NaN) === NaN`). Add explicit NaN check: `const min = sp.min ? (isNaN(Number(sp.min)) ? undefined : Math.max(0, Number(sp.min))) : undefined;`. In `queries/products.ts`, pass the number directly: `gte(products.price, min)` (Drizzle accepts numbers for numeric columns).
- Status: open

## QA-005 — `orderStatusSchema` validator includes `processing` but transition table omits it — creating a validator/logic mismatch

- Severity: **major**
- Where: `src/lib/validators.ts:88-90` vs `src/lib/queries/orders.ts:176-182`
- Problem: `orderStatusSchema` accepts `'processing'` as a valid status:
  ```ts
  status: z.enum(['pending', 'confirmed', 'shipped', 'delivered', 'cancelled'])
  ```
  Wait — `processing` is actually **not** in the Zod enum in validators.ts (confirmed by reading line 89). However the DB enum `orderStatusEnum` in `schema.ts:17-24` **does** include `'processing'`. The `VALID_TRANSITIONS` table in `orders.ts:176-182` has no entry for `'processing'` as a source state. If an order somehow ends up in `processing` status (e.g., manual DB edit, legacy data, future code), calling `updateOrderStatus` returns `allowed = []` (because `VALID_TRANSITIONS['processing']` is `undefined`, so `?? []` applies), meaning the order is permanently stuck with no valid transitions. This is a silent data-corruption risk. The `OrderStatusBadge` component (line 1 of `OrderStatusBadge.tsx`) does include `'processing'` in its type and config, confirming the design intended it to be displayable but the operational logic was never wired up.
- Repro: Manually set an order's status to `processing` in the DB. Open admin order detail → `OrderActions` finds no `TRANSITIONS['processing']` entry → renders `null` → no buttons shown → order stuck forever.
- Fix: Either (a) add `processing` as a valid transition state in `VALID_TRANSITIONS` (e.g., `processing: ['shipped', 'cancelled']`) and add it to `orderStatusSchema`, or (b) remove `processing` from the DB enum entirely. Option (b) requires a migration. Option (a) is safer. Also add a guard in `updateOrderStatus` for unknown source states: throw `InvalidTransitionError(currentStatus, newStatus)` when `VALID_TRANSITIONS[currentStatus] === undefined`.
- Status: open

## QA-012 — Profile update API accepts empty-string phone, bypassing Moroccan phone validation

- Severity: **major**
- Where: `src/lib/validators.ts:95-100` (`profileUpdateSchema`) and `src/app/api/auth/profile/route.ts:33`
- Problem: `profileUpdateSchema` defines:
  ```ts
  phone: z.string().regex(/^(0[67]\d{8}|\+212[67]\d{8})$/).optional()
  ```
  When `phone` is `""` (empty string — the `initialPhone` default in `ProfileForm`), Zod's `.optional()` does **not** skip the regex check for empty string; it only makes the field omittable entirely. An empty string `""` fails the regex but the form sends `phone: ""` when the field is cleared. The API returns a 422 validation error with `fields.phone` = `['Numéro de téléphone invalide']` even when the user simply wants to clear their phone number. There is also no way to remove a phone number once set.
- Repro: Register with phone `0612345678`. Go to profile, clear the phone field, save → 422 error "Numéro invalide" even though the user just wants no phone.
- Fix: Add `.or(z.literal(''))` to allow clearing: `z.string().regex(...).or(z.literal('')).optional()`, and in the API, treat `""` as `null` when updating: `phone: phone === '' ? null : phone`.
- Status: open

## QA-015 — `createOrder` does not validate that `items` array contains unique `productId` values

- Severity: **major**
- Where: `src/lib/queries/orders.ts:55-66`
- Problem: If the same `productId` appears twice in the `items` array (which can happen if the cart store somehow accumulates duplicates, or via a crafted API call), the transaction will:
  1. Pass the stock check twice (each checking independently against the same current stock value, before any decrement).
  2. Insert two separate `orderItems` rows for the same product.
  3. Decrement the stock twice (once per loop iteration).
  This can drive stock below 0 for a product that had exactly the right amount for one unit. Example: product stock=1, items=[{productId:1, qty:1}, {productId:1, qty:1}] — both pass the `stock < quantity` check (1 < 1 is false), two items rows inserted, stock decremented twice → stock = -1.
- Repro: POST to `/api/orders` with body `{ items: [{productId:1, quantity:1},{productId:1, quantity:1}], ...validForm }` for a product with stock=1 → order created, stock goes to -1.
- Fix: Add deduplication/aggregation before the loop: `const aggregatedItems = data.items.reduce(...)` merging quantities for the same productId. Then validate aggregate quantities against stock. Alternatively add a Zod refinement on `createOrderSchema.items` that checks for unique productIds.
- Status: open

## QA-024 — `createOrder` stock decrement is not protected against concurrent orders for the same product

- Severity: **major**
- Where: `src/lib/queries/orders.ts:55-102`
- Problem: The transaction reads stock, checks availability, then decrements. However, between the `SELECT` (line 39) and the `UPDATE` (line 97-102), another concurrent transaction can also read the same stock value and pass the same availability check. If two orders for a product with stock=1 arrive simultaneously, both transactions may read `stock=1`, both pass the `stock < quantity` check (1 < 1 = false), both insert their order items, and both decrement — resulting in `stock=-1`. This is a classic TOCTOU (time-of-check-time-of-use) race condition. The decrement is atomic (`sql\`stock - qty\``), but the prior check is not synchronized with it.
- Repro: Simulate two simultaneous POST requests to `/api/orders` for the same product with stock=1. Both succeed → stock = -1 → product oversold.
- Fix: Use a pessimistic lock on the product rows during the transaction: `SELECT ... FOR UPDATE` in Drizzle via `tx.execute(sql\`SELECT id FROM products WHERE id = ANY(${productIds}) FOR UPDATE\`)` before the stock check. This ensures only one transaction can proceed at a time for the same product. Alternatively, change the stock check to use a `WHERE stock >= quantity` in the UPDATE itself (optimistic lock) and check the `rowCount` of the update result — if 0 rows updated (stock was insufficient at update time), roll back and throw `StockError`.
- Status: open
