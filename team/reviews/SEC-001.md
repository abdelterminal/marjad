# SEC-001 — Security Review (Phase 4)

Reviewer: Security Engineer
Scope: Admin auth, credentials auth, public order creation, image upload, input validation, session security, account IDOR, secrets.
Stack: Next.js 16 App Router · Drizzle ORM · PostgreSQL · NextAuth v5 beta · Zod · bcryptjs · sharp.

Summary: 1 blocker, 3 major, 4 minor, 2 nits.

---

## SEC-001 — Order confirmation page leaks any customer's PII via IDOR
- Severity: blocker
- Where: `src/app/[locale]/checkout/confirmation/[orderId]/page.tsx:17-18` (calls `getOrderById`); query in `src/lib/queries/orders.ts:159-173`
- Problem: The confirmation page is fully public — no `auth()` check, no ownership check. It takes `orderId` straight from the URL, calls `getOrderById(orderIdNum)`, and renders the order. `getOrderById` eagerly joins the `user` relation selecting `name, email, phone` plus the order's own `customerName`, `customerPhone`, `city`, `address`. Order IDs are sequential auto-increment integers, so anyone can walk `/checkout/confirmation/1`, `/2`, `/3`… and harvest every customer's full name, phone number, and delivery address. For a Morocco COD store this is a mass PII / GDPR-equivalent breach and a doxxing vector. This is the single most dangerous issue in the app.
- Fix: Require ownership before rendering. Two-pronged:
  1. For the immediate post-checkout flow, do not key the confirmation on a guessable order id. Either (a) gate the page behind the session and verify `order.userId === session.user.id`, or (b) issue an unguessable token (UUID) for the order and require it in the URL, or (c) for guests, store the just-created order id in an httpOnly cookie/session set during POST and only allow viewing that id.
  2. Add a dedicated `getOrderForConfirmation(id, { userId | token })` query that returns only the fields the confirmation needs and never the joined `user.email`/`user.phone`.
- Status: open

## SEC-002 — No rate limiting on login, registration, or order creation
- Severity: major
- Where: `src/auth.ts:15` (credentials authorize), `src/app/api/auth/register/route.ts:8`, `src/app/api/orders/route.ts:7`
- Problem: There is no rate limiting anywhere (grep for ratelimit/throttle/redis usage = 0 hits), even though `REDIS_URL` is provisioned. Consequences: (a) the credentials login endpoint can be brute-forced / credential-stuffed at full speed; (b) the public, unauthenticated `POST /api/orders` can be hammered to flood the orders table and silently decrement product stock to zero (denial of inventory / business DoS) since each call writes rows and runs `stock = stock - qty`; (c) registration can be used to enumerate and spam-create accounts.
- Fix: Add IP + account based rate limiting (e.g. a small Redis/Upstash sliding-window limiter or `@upstash/ratelimit`) in front of `authorize`, `register`, and `POST /api/orders`. Suggest e.g. 5 login attempts / 15 min / IP+email, 3 registrations / hour / IP, 10 orders / hour / IP. Combine with a stricter bound on order item count and quantity (see SEC-005).
- Status: open

## SEC-003 — String inputs have no maximum length (storage/DoS abuse)
- Severity: major
- Where: `src/lib/validators.ts:23-37` (createOrderSchema: `customerName`, `city`, `address`, `notes`), `:5-10` (registerSchema: `name`), `:52-70` (adminProductSchema text fields)
- Problem: Public order fields enforce only minimums. `notes`, `address`, `customerName`, `city` accept arbitrarily large strings (megabytes). Combined with SEC-002 (no rate limit) an attacker can submit huge unauthenticated payloads to bloat the DB and exhaust memory/bandwidth. `req.json()` is also called with no body-size guard. These values are later rendered (e.g. admin order detail, confirmation) — unbounded attacker-controlled text is a stored-content risk.
- Fix: Add `.max()` to every free-text field (e.g. name ≤ 120, city ≤ 80, address ≤ 300, notes ≤ 1000, product names ≤ 200, descriptions ≤ 5000). Optionally enforce a max request body size at the route level.
- Status: open

## SEC-004 — `images` array on products accepts arbitrary client-supplied strings
- Severity: major
- Where: `src/lib/validators.ts:67` (`images: z.array(z.string())`), used by `POST/PATCH /api/admin/products`
- Problem: The product `images` field is stored verbatim from the request and later rendered as image `src` (e.g. confirmation page `src/app/[locale]/checkout/confirmation/.../page.tsx:77` and product pages). The schema accepts any string — including `javascript:`-style or external URLs / `data:` URIs — not just paths produced by the upload pipeline. Although this endpoint is admin-only (lower blast radius), it means a compromised or careless admin, or any future widening of the writer, can inject arbitrary URLs/payloads into the storefront, and Next/Image config would need to allow them. Defense-in-depth: the trusted upload pipeline returns `/uploads/<uuid>.webp`, so stored image refs should be constrained to that shape.
- Fix: Validate each entry: `z.array(z.string().regex(/^\/uploads\/[a-f0-9-]+\.webp$/)).max(10)`. Reject anything that is not an internally-generated upload path.
- Status: open

## SEC-005 — Order item array is unbounded in length
- Severity: minor
- Where: `src/lib/validators.ts:29-36`
- Problem: `items` enforces `.min(1)` and per-item `quantity` max 99, but there is no cap on the number of distinct line items. A single request can contain thousands of items, each triggering a per-item `UPDATE products` inside the transaction (`src/lib/queries/orders.ts:97-102`), amplifying DB load. Combined with no rate limiting (SEC-002) this is an easy amplification vector.
- Fix: Add `.max(50)` (or a sane catalogue-sized bound) to the `items` array and consider de-duplicating productIds.
- Status: open

## SEC-006 — Weak/placeholder AUTH_SECRET in `.env.local`; no trustHost / prod hardening
- Severity: minor
- Where: `.env.local` (`AUTH_SECRET=marjad-dev-secret-change-in-production`), `.env.local.example`
- Problem: The JWT session strategy signs tokens with `AUTH_SECRET`. The committed-locally value is a guessable placeholder. If this file or value is reused on the VPS, an attacker who guesses/leaks it can forge a JWT with `role: 'admin'` and bypass every guard (middleware + `requireAdminApi`), since admin is determined solely by the `role` claim in the token (`src/auth.ts:31-32`). `.env.local` is correctly gitignored (verified: not tracked), so this is not a leak today, but the deploy must use a high-entropy secret.
- Fix: Generate a 32+ byte random secret (`openssl rand -base64 32`) for production and confirm it is set in the VPS environment, never the placeholder. Add a startup assertion that refuses to boot if `AUTH_SECRET` is the placeholder/missing.
- Status: open

## SEC-007 — bcrypt cost factor 10 is below current recommendation
- Severity: minor
- Where: `src/app/api/auth/register/route.ts:33` (`bcrypt.hash(password, 10)`)
- Problem: Cost 10 is the library default but on the low end for 2025/2026; given password minimum is only 8 chars, offline cracking of a stolen hash is cheaper than it should be.
- Fix: Raise the work factor to 12 (`bcrypt.hash(password, 12)`). Benchmark on the VPS to keep hash time ~250ms.
- Status: open

## SEC-008 — Image upload trusts client-declared MIME type for the allowlist check
- Severity: minor
- Where: `src/lib/images.ts:26` (`ALLOWED_TYPES.includes(file.type)`)
- Problem: The MIME allowlist is checked against `file.type`, which is the client-supplied `Content-Type` of the multipart part, not the actual file bytes. An attacker (admin context) could send a non-image with `Content-Type: image/png`. In practice sharp re-encodes and will throw on a non-image (decode failure), so the bytes are effectively validated downstream and the output is always a re-encoded `.webp` with a UUID name — path traversal and polyglot persistence are well mitigated. Still, the allowlist gives false assurance.
- Fix: Rely on sharp's parsed metadata for the format decision: read `const meta = await sharp(buffer).metadata()` and allowlist `meta.format` against `['jpeg','png','webp']` before encoding. Keep the size cap.
- Status: open

## SEC-009 — Login error timing / behavior differs for unknown vs known email
- Severity: nit
- Where: `src/auth.ts:17-22`
- Problem: `authorize` returns `null` immediately when the user is not found, but runs `bcrypt.compare` (slow) when the user exists. The response is generic (good), but the measurable timing difference allows email enumeration via the login endpoint. Registration enumeration is already handled with a generic 409 message (good).
- Fix: Always perform a bcrypt compare against a constant dummy hash when the user is not found, so the timing is uniform regardless of whether the email exists.
- Status: open

## SEC-010 — `compareAtPrice` not validated against `price`
- Severity: nit
- Where: `src/lib/validators.ts:61-64`
- Problem: `compareAtPrice` (the struck-through "was" price) is validated as a positive decimal but never checked to be greater than `price`. Not a security hole, but a misconfigured/lower compare-at price produces a misleading/negative "discount" in the UI — a trust/integrity nit. Order totals correctly ignore it (server recomputes from `price`), so no price-tampering impact.
- Fix: Add a `.refine` ensuring `compareAtPrice > price` when present.
- Status: open

## Things verified as SOUND (no action needed)
- Price tampering: `createOrder` re-fetches price + stock from DB and recomputes the total in integer centimes; client-supplied prices are never trusted. (`src/lib/queries/orders.ts:34-68`) Good.
- Stock validation + atomic decrement inside a transaction. Good. (Note: stock check and decrement are in the same tx, acceptable; high-concurrency oversell is theoretically possible without row locks — low risk for this scale.)
- Admin defense-in-depth: middleware guard (`src/proxy.ts:15-22`) + per-handler `requireAdminApi()` on every admin route (uploads, products, products/[id], orders/[id], categories, dashboard). Verified all admin handlers call the guard. Matcher keeps `/api/admin` in scope (no dot in path).
- Account IDOR: `GET /api/orders` and the account page scope queries to `eq(orders.userId, userId)` from the session, not the client. (`src/app/api/orders/route.ts:34-46`, `src/lib/queries/orders.ts:108-122`) Good. (The confirmation page is the IDOR hole — SEC-001 — not the account list.)
- Session: JWT strategy, role carried in token, NextAuth sets httpOnly cookie by default. Role check consistent across middleware + guards + schema enum (`customer`/`admin`); registration hardcodes `role: 'customer'` so users cannot self-promote. Good.
- Upload pipeline: 5 MB cap, sharp re-encode to webp (strips EXIF/payloads), UUID filename, writes only inside `/uploads`, never trusts client filename. Good (see SEC-008 for the one refinement).
- Order status transitions enforced via server-side transition table; admin-only. Good.
- Secrets: no secrets in client bundle; `.env.local` is gitignored and not tracked. Good (see SEC-006 for prod secret strength).
- SQL: all queries go through Drizzle parameterized builders / `sql` template params (`ANY(${productIds})` is parameterized). No string concatenation of user input into SQL. Good.
